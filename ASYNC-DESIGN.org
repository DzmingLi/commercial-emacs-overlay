#+title: GNU Emacs 上的 Commercial Gnus 异步设计
#+subtitle: 架构审查与重构提案，2026-10-13

* 结论与状态

采用明确的主线程提交入口，以及隔离的后端工作进程。
前台 Emacs 拥有 Gnus 的阅读状态和界面；工作进程拥有连接、协议缓冲区和
后端的可变上下文。线程交接、状态合并、文章身份和窗口布局分别有一个负责人。

0.5.0 已实现统一 dispatcher、任务终态、IMAP 独立进程、前台标记合并、
Summary 原位缓存刷新，以及内置的阅读控制器、thread-reader、WebKit 和附件
模块。个人配置只选择账户、级别与渲染器，不再使用窗口协调 advice。

这不是所有后端完成迁移的声明。其他后端仍使用旧 Lisp worker；显式原生
Article/移动/删除操作尚有同步路径。Summary 保留缓冲区、来源锚点及用户
过滤条件，当前仍重新应用默认线程折叠策略，未完整保留手动展开状态。
失败标记写入的 journal 只在当前会话内保留，尚非跨重启的持久化 outbox。
下面仍用目标架构描述后续约束，不能把它们全部视为现有实现的保证。

已验证：120 项 ERT；独立子进程的顺序/取消/异常；真实 Migadu 只读扫描与
BODY.PEEK 正文获取（使用私有测试缓存，不修改服务端旗标）；冷启动 WebKit
主线程防护；真实子进程正文到图形 HTML/附件窗口并返回文本的集成测试。
GUI 测试在未包含新增主循环补丁的已安装 Emacs 上通过，验证 dispatcher
本身的线程归属；不等于已修复当前挂起的旧守护进程。

* 审查范围与现场证据

- 对全部 108 个 Lisp 模块进行了结构和调度入口索引：9170 个顶层形式，
  4450 个函数、方法和宏定义；这不是对全部约 12 万行代码的逐行语义审计。
- 审阅了相对首次导入 =17ac9a3= 的全部 25 个本地修改模块，并追踪启动、
  扫描、已读状态、缓存、虚拟组、列表刷新、正文读取和展示的调用路径。
- 检查了 thread-reader、WebKit 适配器、附件面板和只读后端的接口与状态归属。
- 核对了导入版本 =bf4184f985d0674a7c03c12eb33b66ac833d9e29= 的
  Commercial Emacs 原始 C 核心和 timer.el，及 GNU Emacs 31 对应实现。
- 用户现场堆栈显示 WebKit 的进程启动回调触发主 RunLoop 归属断言，产生
  SIGABRT。退出清理又经 process_pending_signals 进入 PGTK 事件分发循环。
- 在已安装的 GNU Emacs 31 上，后台线程的 I/O 等待可以执行到期定时器。
  原版 Commercial Emacs 则有定时器线程字段和对应的执行归属检查。
- 小型隔离实验发现，不能仅凭进程的 thread 属性推断所有输出回调始终在
  主线程执行；本版本在子进程结束的测试中出现过后台线程执行输出回调。
- 主线程事件交接原型在当前已安装版本上通过测试，不需要新增 C 补丁。
  进一步的首次 WebKit 创建和销毁实验也通过，预览回调始终在主线程执行。
  这些早期实验是重构前的证据；重构后新增的验证见开头实现状态。

关键实现位置：

- =lisp/gnus/gnus-start.el=：gnus-scope-globals、后台扫描和发布。
- =lisp/gnus/nnoo.el=：服务器切换及后端变量状态。
- =lisp/gnus/nnimap.el=：连接互斥、响应解析、旗标更新及头部缓存。
- =lisp/gnus/nnvirtual.el=：源文章与临时虚拟编号的映射和标记回写。
- =lisp/gnus/gnus-summary-refresh.el=：后台完成后的重新选组。
- =lisp/gnus/gnus-sum.el=：重新选组、退出、标记和服务器操作。
- =gnus-thread-reader.el=：正文任务、缓存、发布和原始文章地址。
- =gnus-webkit-preview.el=：待加载文章订阅、HTML 预览和导航。

* 当前设计中应消除的耦合

1. 扫描线程捕获的是共享 newsrc/info/hash-table 对象。局部绑定变量名称
   不能隔离这些对象，也不能覆盖 nnoo 的所有后端状态。界面更新被推迟，
   状态修改仍发生在后台。
2. 扫描、正文和线程头部各自管理线程、定时器、取消及回调。普通定时器
   被当作主线程交接，实际没有建立可验证的主线程契约。
3. Summary 刷新通过退出和重新进入组完成。退出会同步标记、处理交叉引用
   并关闭组；缓存读取上下文没有自动消除所有写入及网络路径。
4. 展示组件依赖当前 Summary 缓冲区及可变虚拟编号。刷新时替换缓冲区、
   重新编号，再由多个组件修补关联，生命周期和身份判断分散。
5. 窗口布局由原生 Gnus、thread-reader、预览适配器、用户 advice 和附件
   钩子共同影响。界面组件同时参与获取、标记、导航和窗口管理。

* 模块边界

| 层 | 唯一职责 | 交付给其他层的数据 |
|----+----------+--------------------|
| 后端工作进程 | 网络、协议解析、后端上下文 | 带请求编号与版本的结果 |
| 主线程交接 | 接收、排队、取消、过期结果检查 | 已验证的待提交结果 |
| Gnus 状态适配 | 提交状态、合并服务器旗标和本地操作 | 状态变更及文章快照 |
| 列表与虚拟组 | 从快照生成有排序的视图 | 稳定文章键及投影 |
| 阅读控制器 | 选中项、加载状态、导航、窗口布局 | 指定窗口中的展示请求 |
| 渲染器 | thread-reader、HTML、附件的显示 | 展示完成或失败事件 |
| emacs-webkit | 原生浏览器调用和资源释放 | 浏览器实例或可捕获错误 |

不要为这次重构另建一套已读数据库。Gnus 的 newsrc/info/marks 仍是前台
阅读状态的权威表示；服务端旗标通过适配层同步。内容缓存可以持久化，
但缓存中的缺失正文、缺失头部和过期视图都不能推导出“已读”或“已删除”。

* 调度与 I/O

** 主线程交接

所有状态提交、用户钩子、列表重建、窗口操作和 WebKit 调用都经过同一个
入口。入口必须检查 current-thread；来自其他线程的结果只入队，通知
主线程事件处理器。定时器可以触发入队，不能直接发布界面结果。

已验证的原型使用 thread-signal 的主线程事件和专用事件处理器；正式
实现只处理自有事件，转交其他 thread-event 给原处理器，避免影响别的包。
事件携带已登记任务的编号，任务内容来自自身队列，不在事件中执行任意
外部返回的 Lisp 代码。提交采用防重入、有限批次和明确的事务结束点。

** 工作进程

工作进程使用无个人初始化、无图形界面的 Emacs，加载最小后端配置。
复用现有 nnimap、nnrss、nnatom 及自定义后端协议，不重新编写 IMAP 客户端。
保持直接 IMAP，工作进程不改变收信方式为 Maildir 或 mbsync。

初版按后端/服务器隔离长驻进程，每个进程串行处理自己的任务和连接。
正文任务优先于预取；扫描分批，批次之间允许高优先级任务进入。
连接状态、选择的邮箱、请求编号和协议缓冲区只由其工作进程修改。
进程数量和连接拆分依据实际延迟测量调整，不先引入大量并行连接。

工作进程不能启动完整交互 Gnus、保存主 newsrc、调用展示钩子或打开 GTK。
传统后端若需要 Gnus 上下文，使用工作进程内的临时副本。返回原始远程
变化或明确的快照，不能把整个临时 Gnus 状态直接覆盖到前台。

协议区分结果数据和日志。结果使用明确的数据结构、版本和长度界限，
不 eval 工作进程输出。正文使用字节数据或私有缓存文件；诊断只记录请求、
阶段和错误，不记录密码和邮件正文。

* 状态、身份与缓存

** 请求信封

每个任务至少包含：请求编号、Gnus 会话代次、服务器键、操作、原始组、
原始文章键、后端纪元、请求开始时的状态版本、截止时间及取消状态。
结果至少区分成功、失败、取消及部分结果；完整空邮箱与获取失败必须是
不同的结果，不能共享一个“没有数据”的返回值。

旧会话、旧 UIDVALIDITY、已取消的显示请求和被替换的文章都不能更新界面。
有效的迟到正文仍可进入内容缓存，是否显示由当前阅读请求决定。

** 文章键

IMAP 文章键包含账户/服务器、原始邮箱、UIDVALIDITY 和 UID。
RSS/Atom 等后端包含原始来源及其稳定条目标识；现有原生文章号继续保留。
Message-ID 用作内容一致性检查，不能独自区分跨邮箱副本，也不能代替
UIDVALIDITY。nnvirtual 的临时编号只用于显示映射。

虚拟列表、线程树、正文、附件和用户动作都引用同一个原始文章键。
排序、刷新和只显示未读不会改变该键。虚拟组是来源状态的投影。
日期解析和排序策略集中在视图构建入口，并遵守用户的排序设置；缺失日期
采用持久化的稳定回退值，不用每次抓取完成的时间把旧文章推到列表顶部。

** 本地标记与远程旗标

前台先通过 Gnus 的原生状态接口提交读/未读/标记动作，再排队发送远程
变化。待确认操作具有递增序号。旧扫描结果不得覆盖后发生的本地动作；
旧操作的确认也不得把一个后来改为未读的文章重新设为已读。

读取正文使用不隐式修改已读状态的操作。预取不标记已读。
只有当前选中且成功展示的文章触发一次原生阅读动作。人工改为未读以后，
切换同一文章的 thread-reader/WebKit 展示形式不会再次自动覆盖标记。

所有服务器写入走任务通道。关闭窗口和后台列表刷新不会隐式发送 STORE、
EXPUNGE 或触发新扫描。远程写入的失败、确认和结果不确定状态要显式表示。

* 列表与阅读窗口

列表刷新成为纯粹的快照更新，不再借用“退出组，再进入组”。保留当前
Summary 缓冲区、选中文章键、滚动锚点、用户过滤条件和线程展开状态。
缓存缺失显示加载状态并提交获取任务；显示列表的调用路径没有网络等待。

阅读控制器拥有阅读窗口及当前文章。默认左边列表、右边阅读；正文渲染器
只能接收并使用控制器提供的窗口，不自行拆分整个 frame。
附件面板属于该阅读区域，是否存在以及高度由附件内容和配置决定。

news@dzming.li 的 HTML 策略、i@dzming.li 的 Level 1，以及新闻的 Level 2
是用户配置层的选择。它们通过声明式策略选择渲染器，不通过围绕多个
组件的窗口 advice 协调状态。

加载状态明确为 queued、fetching、ready、error、cancelled。每个请求必须
到达终态。出错时正文区域显示错误和重试动作，不能只改 header-line，
把正文永久留在 Loading。关闭视图只取消订阅，不破坏别的视图正在使用
的正文、MIME 或导出资源。

* 原生 WebKit 的职责

emacs-webkit 的所有 Lisp 暴露入口都检查主线程归属。错误线程上的调用
应在接触 GTK 前返回可捕获的 Lisp 错误，不能静默创建对象或强行异步化
原本同步返回浏览器实例的 API。GC finalizer 继续只安排主 GTK 循环释放。

gnus-webkit-preview 只接收正文快照和目标窗口，导出 HTML/CID 资源并显示。
获取、已读动作、队列和导航目标由阅读控制器提供。它不依赖 thread-reader
的内部 hash-table、当前虚拟编号或原生 Article 缓冲区的可变 MIME 句柄。

* 迁移顺序

1. 建立统一主线程交接、任务状态和真实的对抗测试。先迁移正文发布及
   扫描完成通知，修正这次已经复现的线程错误。
2. 隔离网络后端，增加快照/变化适配器、单一状态提交和远程标记队列。
   保留现有服务器名称、订阅、已读记录和有效的身份/协议解析修复。
3. 把 Summary 刷新改为原位更新；让虚拟组和 reader 共同使用稳定文章键。
4. 合并阅读布局与资源生命周期，再简化预览和附件集成。
5. 删除被上述明确边界替代的线程、局部隔离绑定、重选组修补、重复缓存
   和窗口 advice。GNU API 兼容修复、稳定 Message-ID 和独立底层修复逐项
   评估保留。需要的一次性数据迁移使用单独命令及数据版本，不放入长期 init。

迁移过程保持可分阶段验证。新设计通过关键端到端场景后，再更新配置版本，
统一 rebuild 和重启；测试通过不等于当前已经卡住的进程恢复。

* 验收场景

- 真实缓慢 I/O 与后台线程并存时，正文、扫描提交、窗口和首次 WebKit 创建
  的所有回调均在主线程运行，包括进程结束及异常路径。
- 打开、刷新及滚动缓存列表不调用任何网络函数，不经过选组退出逻辑。
- 显示未读列表时读取一篇文章，随后完成旧扫描，已读状态不会被回滚。
- 连续读、未读、读及乱序确认，最终前台状态和服务端旗标符合最后的动作。
- 刷新重新排序和虚拟编号变化后，正文、回复、附件和标记仍指向原始文章。
- UIDVALIDITY 改变、旧会话完成、切换文章、关闭窗口和取消加载后，迟到结果
  按请求规则处理；失败和取消都会离开 Loading。
- IMAP/RSS、冷启动、缓存缺失、已有缓存、无附件和多附件覆盖相同的阅读
  控制流程。始终只有一个正文阅读窗口，附件面板保有可用高度。
- WebKit 错误线程调用得到 Lisp 错误；创建、销毁与 worker I/O 的真实 GUI
  压力测试不出现 GTK/WebKit 线程归属错误或界面饥饿。

现有 44 项 Gnus 测试、21 项 reader 测试和原生 GUI 压力测试继续作为基础。
必须补充上述完整调用路径和时序测试，避免仅替换 render/mark 函数的测试
掩盖真实的跨线程 UI 操作和列表刷新的远程写入。
